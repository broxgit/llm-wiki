# Roadmap

Potential improvements to the wiki template, in rough order of payoff. Work from the top of Next. When an item is finished, move it to Done with the date and what changed.

Each item says why it matters, a sketch of how, and what is still undecided.

## Next

### Port wiki.sh to Go, one command at a time

- **Why:** see the first step under Done. The aim is one binary that needs no Bash 3.2 workarounds and no Python.
- **Sketch:** the MCP server is in the helper, and still runs `wiki.sh` for `start`, `status` and `sync`, which are most of what `wiki.sh` is. `capture` and `feedback add` are in the helper. The table of `status` is in the helper now; the rest of `status` reads the machine's setup and stays Bash. `start` and `sync` stay in Bash, decided on 2026-11-09 after reading both. `start` launches the background compile and the helper fetch by running `wiki.sh`, so a Go `start` would still need it, and the rest of it is the machine's setup that the `status` port left in Bash: the collection rules, matched as shell patterns, the tips file, the feedback reminder, the `command -v` checks and the compile lock. Porting only its read-only middle would change nothing for the server. `sync` commits through the secret-scan hook, which is Bash, and calls `index` and the lock. Neither would be faster: the remote is most of their time. To get to one binary, port what they lean on first: the launcher of `compile`, the lock, `index` and the hook. Small and separate: `chat_state`, `chat_write` and `mcp --print` still need `python3`, so `wiki setup chat` does too. `find` is ported as it was: index lines, then one line from each of five pages, in the order of their paths. Ranked section results would be new, so they are a change of their own. Still Bash in routing: choosing the collection (`collection_for`, which runs at the top of every command, the core ones included), `wiki_root`, `repo_map` and the `links.md` lookups. Each port prints what the old code prints, checked by the smoke tests, and adds nothing.
- **Open:** whether the desktop app's Chat tab itself runs the helper's server as it ran the Python one: the smoke tests and the Claude CLI can't show that. And when the ported commands may drop their old Bash and Python. The helper now reaches people through `wiki update`, but that has to prove itself first. The core commands (`start`, `capture`, `lock`, `sync`, `index`) stay in Bash until then, so a session can never break over a missing binary.

### Extensions: integrations outside wiki.sh

- **Why:** Obsidian, Jira, Confluence, CI and git hosting are each optional, and each one built into `wiki.sh` is code every user carries. Teams also want to add their own. Decided on 2026-11-10: integrations become extensions, home-grown ones are supported as far as they can be, and the features stay agent-agnostic, with a thin layer for each agent.
- **Sketch:** everything the first two extensions needed is done (see Done): the command seam, events, a sign-in they share, a wiki's content as data, and settings a session can change. GitHub Actions is the third, with GitLab CI and Jenkins after it (all four stages are done, see Done). Still to do: moving `wiki obsidian` out, and a third extension written by someone else as the real test of the contract. An unattended fix for GitLab CI or Jenkins only if it is asked for, with a review of its own: none exists today, and neither extension writes anywhere.
- **Open:** how a team shares extensions. They are per machine on purpose, so a pull can't add a command. A shared collection could carry them behind a step that asks each person once, on each machine, whether to trust each one. Where extensions that ship with llm-wiki live, and whether `wiki update` installs them. How an extension adds a handbook rule without `wiki upgrade` dropping it, and what that costs in context. Whether the helper needs to know about extensions at all.

### A release plan, before a whole team gets it

- **Why:** merging to `main` is the release today, and every user gets it at once. That is fine for a few people and not for a team of a hundred: there is no version to name when something breaks, no way back to the one before, and no way to hold a change until it is ready. Asked for on 2026-11-17: release and distribution that are official and follow current practice.
- **Sketch:** llm-wiki as a whole gets a release version, 1.0 on the day the team gets it, with patch, minor and major meaning fixes, additions, and "read this first". A release is a tag made on purpose, with notes, and `main` may be ahead of it. `wiki update` follows releases, and can go back to one. The handbook keeps its own counter (38 now) as an internal revision that a release carries: setting it back to 1 would put every existing wiki ahead of the template. The changelog before 1.0 folds into one section. What is shipped is signed or checksummed, as the helper already is, and a release is tried on a few machines before everyone gets it.
- **What Claude Code gives us (read in its documentation on 2026-11-17, not tried):** a plugin with no `version` in its manifest has its commit as its version, which is why every merge reaches everyone. With a `version`, a plugin updates only when that string changes. A marketplace can be added at a branch or tag (`owner/repo@ref`), and then follows that ref. There is no command to install an earlier version or to go back: holding people on one is done by the ref they follow. An organization can name the marketplace, its ref and whether it updates by itself in managed settings. `claude plugin tag` makes a release tag and checks the manifest agrees.
- **So, in stages:** (1) try it in a throwaway repository: a `version` in the manifest, a `stable` branch, an update, and going back, since the last is not documented; (2) a `version` in the manifest, a `stable` branch that moves only at a release, a release made by CI from a tag (the whole suite, the helper built and checked against its lock, notes from `NEWS.md`, a build attestation), and `wiki update` saying which version it left and reached; (3) moving the people who follow `main` today onto `stable`, and a way to follow `main` on purpose; (4) a page for an organization: the managed settings that name the marketplace and its ref.
- **Open:** Whether the Codex, Antigravity and Cursor plugins follow the same version. Whether Homebrew becomes a second way to install: it can't run `wiki uninstall`, and two installs can disagree about which version runs, so it waits for the Go port to leave one binary. Whether machine settings get a version of their own with a step that runs when it is behind, which `wiki uninstall` made the inventory for. Who may cut a release, and what has to pass first.

### Obsidian as the home, for people who don't use git

- **Why:** asked for on 2026-11-17: people who are not software engineers want a nice place to keep wikis that is synced and backed up, and Obsidian is that place. An Obsidian vault is a folder of markdown, and `wiki obsidian` already opens the collection as one, so the gap is what such a person needs around it.
- **Sketch:** three parts. The first is done (see Done): a note typed in an inbox folder becomes a note of the wiki. The second is a collection that needs no git: Obsidian Sync or a cloud drive carries it, setup asks no git questions, and `wiki sync` doesn't push, with a local history kept as a safety net the person never sees. The third is a plugin inside Obsidian with buttons for saving, compiling and what needs attention.
- **Open:** for the second part, two things about Obsidian Sync that nobody has checked and that decide the design: what it does with hidden folders such as `.git`, and how it merges a page edited on a phone and by an agent at once. A cloud drive that syncs `.git` can corrupt it. Without git there is no history of what an agent changed and no secret scan before a push. The lock that keeps compiles to one session is a file, and would sync late. Whatever is built reads only the wikis' vault, never another vault.

### Learn where a person works, by asking

- **Why:** llm-wiki assumed a session belongs to one repository. Most of one team starts sessions in a folder for a ticket, which holds clones, and for weeks their project wikis never loaded and nothing said so. Decided on 2026-11-11: never guess silently; ask when unsure; write what is learned into the person's own wiki, so the questions get rarer.
- **Sketch:** steps 1 to 3 are done (see Done): a folder of clones uses their wikis, patterns remember the answer, and a note taken in a ticket folder carries the ticket's key. Step 4 is done too: `wiki setup` asks how you work, and writes the patterns.
- **Open:** how many wikis to read in full when a folder's clones belong to many. Where a ticket's own state goes: the maintainer said "both, maybe", the repo's wiki and the personal journal. Whether a git repository that holds clones is placed as a folder of clones is: a teammate asked on 2026-11-12 about checking her ticket folder into git, and the "home repo" pattern (one repository you always start in, with the others cloned inside it and ignored) has the same shape. Today such a folder is a repository like any other, so the wikis of the clones inside aren't used. Whether a wiki's `repos.md` should say more than a name for each repository: what it is, where it lives on this machine and where to clone it from, so a session in a ticket folder can find or fetch a repository the ticket needs and the folder lacks. Seen on a real ticket the same day. A clone two folders down isn't seen, and two different repositories with one name share a wiki: both found in the first hand test on real ticket folders, neither decided.

### Know whether sessions capture and compile

- **Why:** `wiki stats` measures lookups only. Saving and compiling are the parts that failed in the first week (50 of 109 notes never compiled), and nothing measures them now.
- **Sketch:** `wiki status` flags a wiki whose repository has commits in the last two weeks but no new notes in that time.
- **Open:** wait for two weeks of `wiki stats` first. It may not be needed.

## Later

- **Find repeated work in transcripts.** Scan the transcripts on disk (`~/.claude/projects`, Antigravity's) for command sequences repeated across sessions, and report them as candidate toil. Look at this only if handbook v32 still misses repeats.
- **Merge requests in standups.** Reviews and MRs opened live in GitHub or GitLab, not in git history. Pulling them in would need an API token and a host per remote.
- **Backfill from more places.** The desktop app's Chat tab and claude.ai aren't on disk, so they're out of reach without an agent that has chat search. (The desktop Code tab is in `~/.claude/projects`, and Gemini's Antigravity conversations are read since 2026-10-29.)
- **A hosted MCP server,** so web agents can search everything and save notes. A claude.ai Project covers reading for now. Build this only if saving notes from the web keeps coming up: it puts private notes behind a public URL, so it needs sign-in and a security review first.
- **Team digest.** A weekly roll-up across several people's journals, for a lead. Needs a shared, opt-in journal location.
- **Review flow for teams.** Agents push straight to the collection. A team may want a weekly digest of changes, or pull requests.
- **Microsoft 365 Copilot through gitlab.com.** Parked on 2026-11-03; the code is on the `microsoft-copilot-gitlab` branch. It worked once, signed in as an account in a paid company group, but GitLab's server follows the signed-in account, so the agent could read everything that account can. A dedicated Reporter account should fix that, but a free one, owning its own free group with MCP access on, gets a 403: "MCP server not enabled for any of your groups". Revive this if GitLab explains that denial, or if an account in a group that counts can be limited to one project. Until then, the GitHub route is the way: code can stay on GitLab, with only the wikis the agent reads on GitHub.
- **Terse page style.** Held on 2026-11-02. Measured on one sample page, terse plain-word notes used 56% of the tokens of default prose, but wiki reads were about 1.9% of a week's new input tokens, so the saving is under 1%. It would mean rewriting every page or keeping two styles, and teammates read the pages too. If token savings become a goal, look at long sessions first: most of the volume is cache reads. If it ever comes back, test answer quality first, and skip abbreviations and JSON, which saved nothing more in the same test.

## Decided against

- **Embeddings or a vector database.** Lookup by repository name plus keyword search covers the need. Embeddings also tie the data to one embedding model.
- **A custom UI.** Obsidian and GitHub already render markdown.
- **More scaffolding automation.** Setup is one command.

## Done

### An inbox: notes a person types become notes of the wiki (2026-11-17)

- **Why:** the only way into a wiki was through an agent's session. A person who would rather type a note, in Obsidian or on a phone, had nowhere to put it.
- **What changed:** a markdown file in a folder called `inbox`, in a wiki or at the top of the collection, is taken into `raw/` by `capture` and waits to be compiled like any other. `start`, `pending` and `compile` take what is ready, `wiki inbox` does it and says why anything was left, and `wiki obsidian` makes the collection's inbox. A note is claimed by a rename, read only once it is known to be a small plain file, removed only after it is saved, and put back if anything goes wrong. "Unchanged for two minutes" is by the time this machine last saw the file change, which a sync can't set back.
- **Still untested:** with a real Obsidian vault and a real sync. Whether a sync client touches files often enough to keep a note waiting is not known; `wiki inbox --now` is the way out if it does.

### Comments on merge requests and pull requests reach a session (2026-11-17)

- **Why:** asked for on 2026-11-17: an agent with no watching of its own never learns that someone commented on its user's merge request.
- **What changed:** with `comments = yes`, off by default, `wiki gitlab` and `wiki github` leave one line for the next session on the branch: how many comments, from whom, and the command that prints them, never what was written. `wiki gitlab comments` and `wiki github comments` print them, each line marked as text from outside. A review found a name check in all three CI extensions that let a trailing newline through; names are now tested whole.

### `wiki jenkins` works out a clone's job from its remote (2026-11-17)

- **Why:** where jobs are named after the repository, as in an organization folder, naming the job for every clone is the same sentence a hundred times. Found on the first try against a real Jenkins, which also showed that a job named after a GitLab path (`group%2Fapp`) was refused.
- **What changed:** `job_pattern`, such as `Platform/{path}`, names the job for a clone with a `Jenkinsfile`; `job_remote` limits it to a host and group; `job_auto` watches such a clone when a session starts in it. A job's name may hold `%XX`.

### A session offers the CI extension that fits the repository (2026-11-17)

- **Why:** an extension nobody turns on does nothing, and the people it would help most don't know it is there.
- **What changed:** an extension says what it is for in a `wiki-detect:` comment. A session that starts in a matching clone is told to offer it, once in a session and in two sessions at most, and `wiki extensions offer <name> no|never|again` keeps the answer.

### Extensions: GitLab CI and Jenkins, stage 4 (2026-11-16)

- **Why:** the last of the four stages decided for the CI extensions on 2026-11-10: GitHub had `check`, the excerpt, the notice, the desktop notification and the note for a fix, and teams on GitLab or Jenkins had nothing. Decided with the maintainer: read-only, with no unattended fix, because that is the part that needs a review of its own.
- **What changed:** `extensions/ci_common.py`, a plain module beside the extensions (no header and no `wiki-` name, so it is never listed or run), holds what is not about one system: cleaning text from outside, the excerpt and its signature, the private excerpt folder and its pruning, the settings file, the notice and the desktop notification, the note for a fixed failure, the state file and the watch list. `wiki-github` imports it; everything about its unattended fix stayed in `wiki-github`, and the existing GitHub tests pass without a change to a check (two tests that patched a function now living in `ci_common` patch it there). `wiki-gitlab` talks to GitLab only through `glab api --method GET` run in the clone (and `glab auth status`): the newest pipeline of each kind on the clone's branch, the default branch and the branch of each open merge request you opened (a fork's is left out), its failing jobs (one allowed to fail is counted apart), and the tail of the failing job's log, GitLab's section markers and escape codes taken out. `wiki-jenkins` talks to Jenkins' JSON API with `urllib`, GET only, as `wiki-jira` does: `url`, `user` and `token_cmd`, with Jira's rules (the token is never printed, logged or stored, `--wiki-settings` never runs `token_cmd`, `--wiki-set` refuses a token and takes `token_cmd` only as `keychain`), `https://` anywhere or `http://` on this machine only, no redirect to another host, a job named with its path (checked strictly) and watched together with a folder, a multibranch project looked at for the clone's branch and the default branch, `FAILURE` and `UNSTABLE` told apart, the stage from Pipeline's API when there is one, and a console read only at its tail (`Range: bytes=-2000000`, and a server that ignores it is streamed, keeping the last 2 MB). Both have `check`, `watch`, `unwatch`, `config`, the tick with its notice and desktop notification, `remember`, and `setup` and `--wiki-*` as the others. Nothing in `cmd/` or `internal/` changed. The setup guide grows by the two extensions' lines (`setup: the whole guide`, +265 bytes), so the guide's cap in the smoke test moved from 6,700 to 7,000.
- **A second review of Jenkins:** the address and the user are settable from a session only while they have no value, and `token_cmd` is neither set nor cleared from one (the first review's lock, on a token being set up, could be undone by clearing `token_cmd`); a `206` whose range starts at byte 0 keeps its first line; and signed in means Jenkins says `authenticated` with a name. GitLab reads at most 20 pipelines and keeps 5 kinds for a ref, `check` has the tick's time for a project, ids must be positive, and glab runs without git's variables.
- **A third review:** the "settable while empty" rule still leaked, so `url`, `user` and `token_cmd` are refused from a session always, and the address is checked with `urlsplit` wherever it comes from.
- **A security review, and what it changed:** a session could point `wiki jenkins` at another address and have the token sent there (now `url` and `user` can't be set from a session once a token is set up, and the address must be set before `token_cmd keychain`); a console full of unclosed notes took quadratic time (now one linear pass); deeply nested JSON, and items or lists of the wrong type, crashed a call (now an unreadable answer, or the item is skipped); one unreadable project stopped the tick for the rest (now it is skipped, the event is 75 only if none could be read, and a project gets 60 seconds and ten merge requests); a GitLab project's name came from the server (now from the clone's origin, which the server must agree with); the state was written without a fresh read under the lock; a trimmed excerpt lost the failure before the tail (now the tail gives way first, which also changes `wiki github`'s excerpt in that one case); a name or text that starts with `-` could become an argument; and a notice's fixed words could use up its limit.
- **Still untested:** nothing here has run against a real GitLab or Jenkins. `glab`'s own words for a failure (not signed in, not a clone, offline) and its configuration file's layout are taken from its help and from what other programs print, and the tests use a stand-in; the real `glab api` was never called. Jenkins: whether a real server honours the `Range` header on `consoleText` (the stream fallback covers one that doesn't), the double encoding of a branch with a slash in a multibranch job's address, and `wfapi/describe` across Pipeline plugin versions, are from documentation and a stand-in server only.

### A session can't change where the Atlassian token is sent (2026-11-16)

- **Why:** a security review of the new Jenkins extension found that a session could set the address its token is sent to, and the same was true of the Jira and Confluence extensions on main since the guided setup: `wiki extensions set jira site <address>` was open to a session, so one that had been misled could point the extension at a server of its own, and the next check or background tick would hand the token over.
- **What changed:** once anything gives the extension a token (a token variable, or `token_cmd`), `--wiki-set site`, and Confluence's `url`, is refused, also for clearing it, and the settings list shows it as for a terminal. An `http://` address is taken only for this machine.
- **Also closed, on the maintainer's word (2026-11-16):** `token_cmd` is never set from a session, not even to the keychain preset. Where the keychain already held a token and llm-wiki had no settings, a session could otherwise have set an address of its own and then the preset. The guided setup now ends with one command for the user: `wiki extensions setup <name>`. A session may still clear `token_cmd`, which only takes access away. This replaces the rule of 2026-11-13 that a session may set `token_cmd` to the preset `keychain`.
- **A second review tightened it (2026-11-16):** the address (Jira's `site`, Confluence's `site` and `url`, Jenkins' `url` and `user`) is settable from a session only while it has no value, from any source (the environment, the extension's file, the shared file), and then changed or cleared only in a terminal; `token_cmd` is neither set nor cleared from a session. Clearing `token_cmd` had unlocked the address, and a token only in the scheduler's environment was never seen by the session's lock.
- **A third review found the "while empty" rule still leaked** (Confluence's `url` counted as empty while the site was in use and then won; a token left from the other Atlassian extension made a session's first address usable at once; `https://real.example@evil.example` was taken as an address). So sign-in settings are for a terminal only: `site`, `email` and `token_cmd` (Jira); `site`, `url`, `email` and `token_cmd` (Confluence); `url`, `user` and `token_cmd` (Jenkins) are refused from a session whatever they hold, and every address is read by `urlsplit` (https, or http only for this machine; a host; no login, query, fragment or space) from a person, a file or the environment, and one that fails stops the command with exit 1 before a token is fetched.
- **Still open:** the terminal check is a guard, not a lock: a session with a shell can edit the settings file by hand.
- **A fourth review, of the rule as it now stands, found it complete, and one older hole beside it:** Jira and Confluence followed a redirect with the sign-in attached, to any host. They now follow one only to the same address, as the Jenkins extension did from the start. Also: `config` checks the address before it fetches the token, an address with a space in front is a fault, and a watched Confluence space's key is only what a key can hold.

### Extensions: an unattended fix for a failed CI run, stage 3 (2026-11-16)

- **Why:** a failed CI run was reported and left for a person. Decided with the maintainer: an opt-in unattended fix, where the agent only edits files and llm-wiki itself checks, commits and pushes. It is the first time an agent's change is committed and pushed with nobody watching, and the first time `wiki-github` writes to GitHub, so it is narrow and refuses over guessing. A security review found holes in the first build (checks that read working files and the index after the agent had run, repository hooks run on the agent's changed code, a push to the name `origin`, a fork's run on a same-named branch); the build was reworked on one principle: after the agent ends, llm-wiki freezes the change into git objects, checks the objects, and builds and pushes the commit from them.
- **What changed:** `wiki github fix [on|off] [<folder>]`. `fix on` asks at a terminal only (stdin a terminal; `LLM_WIKI_TEST_TTY` counts only when the settings file's folder is not the real `~/.config/llm-wiki`; refused from a known agent's shell), for a clone that is watched; `unwatch` turns fixing off and `watch` never turns it on. Six settings (`fix`, `fix_agent`, `fix_model`, `fix_allow`, `fix_max_files`, `fix_max_lines`) are `terminal`, refused by `--wiki-set` with exit 2. When the tick finds a newly failing run, not stale, on the default branch or the head of an open pull request you opened in the same repository, with no attempt on record, fewer than two failed ones since the workflow passed, none running and no earlier pass on the same commit, it asks GitHub about the run itself (`gh api repos/<o>/<r>/actions/runs/<id>`: head repository, sha and branch must match), stores the clone's push address (it must be GitHub's, for exactly this repository, in one of three forms), and decides and records the attempt in one step under the state lock, then starts `wiki-github --fix-run` detached. The run fetches that branch from the stored address, makes a mode 700 worktree and records its `.git`, its folder in `.git`, the author and a fingerprint of the clone (refs, config, hooks, `info/exclude`, `info/attributes`, the user's git config files, the worktree's folder). The agent runs there: claude with `Read`, `Edit`, `Grep` and `Glob` each limited to the worktree, `--setting-sources user --strict-mcp-config` and one `Bash(<cmd>:*)` for each allowed test command, or `sh -c` for another agent; with only its own sign-in left of anything secret-like, and its `origin` made unreachable, for 15 minutes. Then, with `GIT_DIR` and `GIT_WORK_TREE` named, no fsmonitor and no hook: `.git` and the admin folder are checked, the fingerprint is compared, the index is reset to the failing commit, the changed paths staged, and `write-tree` gives the frozen tree. Every check reads objects (`diff-tree --raw` and `--numstat`, `cat-file -s`, `diff -U0` parsed as bytes): file and line limits, never-list paths (`.github/`, CI files, `.claude/`, `.mcp.json`, `.gitleaks.toml`, keys, git's control files), links, submodules, binaries, new executables, deleted tests, and the added lines against the built-in secrets scan, plus gitleaks on the changed blobs in a private folder outside the worktree when installed. The agent's last line is scanned before it is used. The commit is made with `commit-tree` (no hook, one parent, checked) with the clone's author, and pushed by id with `--no-verify` to the stored address, never forced, after the address, the fingerprint and the attempt's claim are checked once more. For the default branch it is a new `llm-wiki/fix-<run id>` and `gh pr create`. The outcome replaces the notice, shows a desktop notification, and the later `ci-fixed` note says the fix was unattended. The repository's own commit and push hooks do not run, on purpose. Nothing in `cmd/` or `internal/` changed.
- **A second review, and what it changed:** a control character inside a short secret dodged the scan of the agent's last line (now cleaned first); the agent's raw output was kept for seven days (now read in memory, 1 MB at most, never written, and the agent can't write a file over 50 MB); a tick's stale copy of the state could write a finished attempt back as running, or the sweep could delete a live worktree (now the disk's copy is final for a finished attempt, and the sweep, `fix off` and `unwatch` work under the lock on the disk's copy); an unlockable state file started a fix anyway (now it starts none); `git remote get-url --push` followed a `pushInsteadOf` anywhere (now the effective address must be GitHub's too, with a test-only switch for a local path in the temporary folder); binary and added lines depended on git's attributes (now decided from the objects, with `git diff -a`); a branch that kept moving cost fifteen minutes of agent each run (now every attempt in which the agent ran counts); abandoned worktrees were swept only with fixing on (now always); git's environment and the clone's alternates, grafts, shallow, replace refs, `commondir` and `gitdir` are guarded; more files that run code or steer agents are refused.
- **A third review (the recommended setup: claude, no `fix_allow`), and what it changed:** dependency and build files (`package.json`, `go.mod`, `Makefile`, `Dockerfile` and the like) are refused unless a person sets `fix_build` at a terminal; more files that steer CI, releases, owners and agents are always refused, with trailing dots and spaces in a name ignored; before the agent starts (so as no try) a worktree holding a link that points outside it, or a sparse-checkout clone, is skipped; text from GitHub and the agent can't act as markup (code spans in the pull request body, `(at)` and `# 123` in the commit and title) and sits in double quotes in a notice, cut by bytes; no record of a fix is written without the lock; a signature of only dashes is never passed to `wiki find`; a fork's newer run on the default branch no longer hides an older real failure.
- **Limits, plainly:** with a command in `fix_allow`, or with an agent other than claude, the agent runs code with your account's rights while it works. It could then do anything you can, including push by itself with your own sign-in. llm-wiki's checks on the result stop mistakes in that case, not a determined attack: the time-of-check windows against a detached child that can write anywhere as the user are not closed. With claude and no `fix_allow` the agent can only read, search and edit its own copy of the code, and everything it produces passes through the checks. That is the setting to choose. A non-claude `fix_agent` is still run through `sh -c`, as the background compile is: it is the user's own trusted command. A fix can still change tests by editing them (emptying one, adding a skip): a deleted test file is refused, an edited one can't be judged. Whatever a fix changes, your CI then runs it, which is also why the log that prompted it matters: a log an outsider can write into is a way to steer the fix. Turning fixing off stops a running fix before it pushes, unless the push has already begun. Read every fix.
- **Tried for real (2026-11-16):** end to end on a private repository made for it, with the real claude (sonnet, no `fix_allow`), the real `gh`, a real push and the real gitleaks. A typo on a pull request's branch: one tick saw the failing run and started the fix, and within a minute one commit changing one line was on the branch, by the clone's author, with CI passing on it; the watched clone's commit, branch and an uncommitted file were untouched, and the worktree was gone. A breaking commit on the default branch: a new branch `llm-wiki/fix-<run id>` and a pull request against it, the default branch itself unchanged, CI passing on the fix. `fix on` with no terminal was refused. Separately, with the real claude and the exact command built here: reading, searching and writing outside the worktree are refused, as is reading or writing through a link that points outside; a hook in the repository's own `.claude/settings.json` does not run; and a `Bash(<cmd>:*)` rule does not allow chaining an interpreter, a shell or a pipe onto the command.
- **Still untested:** a refusal on real GitHub (each is covered by stand-ins only); the schedule driving a fix (the ticks were run by hand); an agent that is not claude and its own sandbox; how `Bash(<cmd>:*)` behaves across Claude Code versions; a clone whose origin is on a GitHub Enterprise host other than `GH_HOST`, LFS, submodules, and commit signing (the commit is unsigned); that the check right before the push (address and fingerprint again) can't be tripped by anything the agent can do, so it has no test of its own; `RLIMIT_FSIZE` where the system has none; and whether a pseudo-terminal in an agent's shell is told from a person's by more than the variables listed.

- **Why:** the journal starts empty on the day it's turned on. Past sessions held the work that left no commit.
- **What changed:** `./wiki.sh journal backfill` digests Claude Code transcripts into `journal/backfill.md`, one block per project per day: prompts, files changed, whether it committed, the last reply. Agents turn the digest into entries per the new Backfill section of `rules/journal.md`. `journal note` takes `--day` and `--at`. First real run: 42 project-days over two weeks became 17 entries. It led to two digest fixes: drop prompts written by tools (task notifications, side-session events), and file sessions from scratch folders under the project they ran in.

### Step-by-step setup (2026-10-22)

- **Why:** setup was five commands plus hand edits, and nothing told an existing machine when a template update added a setting.
- **What changed:** `./wiki.sh setup` walks through the collection, git (repo, remote, commit email, a per-repo SSH key, a test push), the Claude Code session line, handbook upgrades, and every journal setting, with validation and re-asking on bad input. It records answered questions per machine in `~/.config/llm-wiki/setup`, so `setup --new` asks only about what's new. `setup --list` shows every value and marks defaults. `setup journal.format` (or `setup format`) edits one setting. `upgrade` ends with a summary: which wikis moved from which version, the `CHANGELOG.md` entries since then, and next steps (commit command, stale session line, new settings, restart running sessions). `status` and `upgrade --all` say when there is something. Journal settings now come from one registry in `wiki.sh`, so a new setting is one line. Handbook unchanged, still version 9.

### Work journal and standups (2026-10-22, handbook version 9)

- **Why:** engineers need a daily summary for standup. Version 8 stopped capturing finished work, so the wikis alone can't supply one.
- **What changed:** `./wiki.sh standup` gathers the user's commits across repositories, journal entries, wiki notes and changes, work in progress, and open checks. The agent writes it up as a standup, a summary, or a detailed report, per `rules/journal.md`. Agents add one journal line per stopping point for work that leaves no commit. On by default, not committed by default. Thirteen settings in `~/wikis/journal/config`.

### Fixes from the first week of real use (2026-10-07, handbook version 8)

- **Why:** a review of the live collection after six days. Ten wikis, 109 captured notes, 53 pages. Four things had gone wrong.
- **Compile wasn't firing.** 50 of 109 notes were never compiled, and five wikis had an empty index. Long working sessions never reach a "pause". Compile now also runs at session start and whenever five notes are waiting.
- **Capture was too eager.** One build session wrote 27 notes in a day, each its own commit. "Finished work" is no longer a trigger. Notes cover decisions, direction, and what the code doesn't show, at stopping points. Captures are committed with the next compile.
- **Lint never ran.** 58 ingests, no lint. Agents don't count log entries unprompted. Every compile now ends by counting, and `./wiki.sh status` flags `lint due` and `compile due`.
- **Timestamps were invented.** Several notes carried round times. The capture step now says to read the clock and never estimate.

### Wikis that cover several repositories (2026-10-01, handbook version 7)

- **Why:** the first real use was a product spread over several repositories. One wiki per repository sent sessions to the wrong wiki and split the same fact across two.
- **What changed:** a wiki covers a project. That is one repository by default, or several listed in its `repos.md`. Sessions resolve a repository to its wiki by name, then by listing. `./wiki.sh cover` and `./wiki.sh which` manage and query the mapping. The staleness rule now covers facts checked against a cited source, not only against code. `./wiki.sh claude` replaces its own older line.

### Core handbook plus on-demand rules (2026-09-30, handbook version 6)

- **Why:** the handbook loaded in full in every session, about 3,800 tokens, and a third of it went unused.
- **What changed:** `template/AGENTS.md` now holds only what every session needs, about 2,500 tokens. Compile, conflicts, lint, and peer-wiki rules moved to `template/rules/` and are read on demand. The skill no longer embeds a copy of the handbook, which cut it from about 5,300 tokens to about 1,500 and removed a second copy to keep in step.

### Stale-knowledge guard (2026-09-30, handbook version 6)

- **Why:** code changes and pages don't. A stale page that answers confidently is worse than no page.
- **What changed:** pages carry `verified` and `commit` stamps. Before acting on a claim about code, the agent checks it against the code when the code is at hand, and files a correction if it no longer holds. Answers from pages verified more than 90 days ago say so. Lint flags pages past 180 days. `./wiki.sh stale` lists them.
